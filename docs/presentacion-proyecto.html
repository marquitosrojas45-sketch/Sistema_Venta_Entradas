1. Objetivo del Proyecto y Evolución Arquitectónica (TP1 a TP7)

Evolución

El Problema de Dominio: Venta Concurrente de Entradas con Stock Limitado

En la venta de entradas para eventos de alta demanda, múltiples usuarios intentan adquirir simultáneamente las últimas localidades disponibles. Sin mecanismos adecuados de exclusión mutua y desacoplamiento, se producen condiciones de carrera (race conditions), sobreventa (stock negativo) y fallos en cascada. Nuestro sistema evoluciona desde una API monolítica hasta 3 microservicios independientes que garantizan consistencia, seguridad y resiliencia.

Fase 1: Base Monolítica (TP1 - TP3)

  • TP1: Servidor Express con variables .env y cifrado en tránsito HTTPS.
  • TP2: Exclusión mutua en Redis (SET NX PX 5000) y liberación atómica mediante Script Lua.
  • TP3: Persistencia MongoDB con Mongoose, logging rotativo en Winston y Swagger UI.

Fase 2: Microservicios y Docker (TP5 - TP6)

  • TP5: Descomposición DDD en User, Inventory y Checkout Service. Matrices de propiedad y acoplamiento.
  • TP6: Contenedores con Docker Compose, red backend-net, volúmenes y healthchecks.
  • Encapsulación del Lock: Inventory centraliza el stock en MongoDB y el Lock en Redis.

Fase 3: Seguridad JWT y RBAC (TP7)

  • Registro Seguro: Hashing con bcryptjs (10 rondas) y emisión de JWT (HS256) en User Service.
  • Validación Stateless: Verificación autónoma de firma y expiración en cada servicio.
  • Propagación y RBAC: Propagación de JWT desde Checkout hacia Inventory y control de roles.

▼ Redis (Locks) + ▼ MongoDB (Stock)

Principio de Propiedad de Datos (Database per Service)

  • Usuarios (MongoDB tp6_usuarios): Propiedad exclusiva de user-service.
  • Catálogo y Stock (MongoDB tp6_inventario): Propiedad exclusiva de inventory-service.
  • Locks de Stock (Redis inventory-redis): Uso interno exclusivo de inventory-service.
  • Contexto de Sesión (JWT): Emitido por user-service y verificado criptográficamente en memoria.

Bajo Acoplamiento y Alta Cohesión

  • Desacoplamiento de Identidad: Ni Checkout ni Inventory necesitan llamar a User Service durante una compra.
  • Desacoplamiento de Concurrencia: Checkout desconoce Redis y delega la reducción de stock a Inventory vía HTTP REST.
  • Estabilidad: User e Inventory tienen acoplamiento eferente nulo (Ce = 0, I = 0.00).

3. Microservicio 1: User & Identity Service (Puerto 3000)

User Service

Responsabilidades y Reglas de Negocio

  • Registro (POST /auth/register): Valida campos obligatorios, longitud mínima de contraseña (>= 6) y unicidad de DNI y mail (409 Conflict).
  • Hashing Criptográfico: Aplica bcrypt.hash(password, 10) y oculta passwordHash en el método toJSON.
  • Login y Emisión JWT (POST /auth/login): Emite token firmado con HS256 con claims sub, role, iss, iat y exp.

Control de Acceso (RBAC) y Propiedad del Recurso

  • Listado Global (GET /api/usuarios): Exclusivo para el rol ADMIN (403 Forbidden a usuarios comunes).
  • Propiedad del Recurso (GET /api/usuarios/:id): Un USER solo puede consultar su propio ID (req.user.sub === req.params.id).
  • Baja de Cuentas (DELETE /api/usuarios/:id): Exclusivo para ADMIN.
const payload = { sub: usuario._id.toString(), role: usuario.role, iss: 'user-service' };
const accessToken = jwt.sign(payload, JWT_SECRET, { algorithm: 'HS256', expiresIn: JWT_EXPIRES_IN });

4. Microservicio 2: Inventory & Stock Service (Puerto 3001)

Inventory Service

Propiedad del Stock y Concurrencia

  • Catálogo Público (GET /api/inventario): Consulta de eventos y entradas disponibles.
  • Carga Administrativa (POST /api/inventario/stock): Creación o reposición de stock exclusiva para ADMIN.
  • Reducción Concurrente (PUT /api/inventario/reducir): Encapsula el Lock en Redis y el decremento atómico en MongoDB.

¿Por qué el Lock de Redis vive en Inventory Service?

  • Coherencia con el Dominio: Inventory es el único dueño del stock; ninguna capa externa debe manejar bloqueos sobre su dato.
  • Prevención de Sobreventa: Adquiere el lock con SET NX PX 5000; si está ocupado devuelve 409 Conflict de inmediato.
  • Liberación Atómica: En el bloque finally, un Script Lua valida el ownerId antes de borrar la clave.
lockAdquirido = await redisClient.set(lockKey, ownerId, { NX: true, PX: 5000 }); // Si es null -> 409 Conflict
const item = await Inventario.findOneAndUpdate({ producto: nombreProd, stock: { $gt: 0 } }, { $inc: { stock: -1 } }, { new: true });
const scriptLiberacion = `if redis.call("get", KEYS[1]) == ARGV[1] then return redis.call("del", KEYS[1]) else return 0 end`;

5. Microservicio 3: Checkout & Transaction Service (Puerto 3002)

Checkout Service

Orquestación de Compras y Propagación JWT

  • Fachada Transaccional (POST /api/comprar): Recibe la orden de compra del cliente autenticado.
  • Diseño Stateless: Sin base de datos ni Redis propio; delega la validación de stock a inventory-service.
  • Propagación del Token: Reenvía Authorization: Bearer <token> hacia Inventory para mantener auditoría completa.

Timeout Explícito y Semántica de Errores

  • Timeout de 3000 ms: Usa AbortController para abortar llamadas lentas hacia Inventory.
  • Traducción Semántica: 200 OK (compra exitosa), 409 Conflict (lock ocupado), 400 Bad Request (stock agotado), 404 Not Found (producto inexistente) y 503 Service Unavailable (timeout o caída).
const controller = new AbortController(); const timeoutId = setTimeout(() => controller.abort(), 3000);
const response = await fetch(`${INVENTORY_SERVICE_URL}/api/inventario/reducir`, {
  method: 'PUT', headers: { 'Content-Type': 'application/json', 'Authorization': `Bearer ${req.rawToken}` },
  body: JSON.stringify({ producto }), signal: controller.signal });

6. Análisis de Fallos Parciales y Resiliencia en el Flujo de Compra

Fallos Parciales

Secuencia del Escenario de Fallo Parcial Distribuido

  • 1. Participantes: Cliente → checkout-service → inventory-service (Redis + MongoDB).
  • 2. Cambio de Estado: Inventory adquiere el lock, descuenta el stock en MongoDB (de 1 a 0) y libera el lock.
  • 3. Punto de Falla: Corte de red antes de que el 200 OK llegue a Checkout.
  • 4. Inconsistencia: Checkout aborta a los 3000ms y devuelve 503, aunque el stock ya fue descontado en BD.

Mecanismos de Recuperación y Compensación

  • 1. Claves de Idempotencia (Idempotency-Key): UUID único de operación para que ante un reintento Inventory devuelva la confirmación previa sin descontar dos veces.
  • 2. Patrón Saga: Transacción compensatoria (POST /api/inventario/reponer) disparada ante el aborto de la compra.
  • 3. Mensajería Asincrónica: Colas durables (RabbitMQ / Kafka) con confirmaciones ACK.

Aislamiento de Fallos ante Caída de Dependencias

Si el contenedor de inventory-service se detiene, checkout-service no finaliza su proceso: registra el fallo en Winston y responde controladamente HTTP 503 Service Unavailable, recuperándose automáticamente en cuanto Inventory vuelve a estar en línea.

7. Contenerización e Infraestructura con Docker Compose

Docker Compose

1. Imágenes y .dockerignore

  • Imagen base liviana node:20-alpine.
  • Instalación reproducible con npm install --omit=dev.
  • Archivos .dockerignore que excluyen node_modules, .env, logs y certificados.

2. Red Interna y Seguridad

  • Red privada backend-net con resolución DNS por nombre de servicio.
  • Solo se publican al host los puertos 3000, 3001 y 3002.
  • MongoDB y Redis permanecen aislados sin exponer puertos al host.

3. Volúmenes y Healthchecks

  • Volúmenes persistentes nombrados: users_mongo_data e inventory_mongo_data.
  • Arranque coordinado mediante healthcheck y depends_on: condition: service_healthy.
Entorno Docker Compose -> MONGODB_URI=mongodb://inventory-db:27017/tp6_inventario | REDIS_URL=redis://redis:6379
Entorno Local Node.js  -> MONGODB_URI=mongodb://127.0.0.1:27017/tp6_inventario    | REDIS_URL=redis://127.0.0.1:6379

8. Matriz RBAC, Logging con Winston y Documentación OpenAPI

RBAC & Swagger

Matriz de Control de Acceso Basado en Roles (RBAC)

  • User Service (:3000): /health, /auth/register y /auth/login públicos; GET /api/usuarios/:id propio o ADMIN; GET /api/usuarios y DELETE exclusivo ADMIN.
  • Inventory Service (:3001): /health y GET /api/inventario públicos; POST /api/inventario/stock exclusivo ADMIN; PUT /api/inventario/reducir USER o ADMIN.
  • Checkout Service (:3002): /health público; POST /api/comprar USER o ADMIN.

Observabilidad y Documentación Interactiva

  • Logging Estructurado (Winston): Registra timestamp, severidad (INFO, WARN, ERROR), servicio y metadatos de auditoría. Consultable con docker compose logs -f.
  • Portales Swagger UI (OpenAPI 3.0):
    • http://localhost:3000/api-docs
    • http://localhost:3001/api-docs
    • http://localhost:3002/api-docs

9. Suite de Pruebas Reproducibles Automatizadas y Conclusiones

Validación y Tests

Ejecución Automatizada de Punta a Punta (npm test / node tests/test-reproducible.js)

  • Fase 1 (Healthchecks): Comprueba la salud de los 3 microservicios y sus conexiones a MongoDB y Redis.
  • Fase 2 y 3 (Identidad y Preparación): Registra y autentica usuarios ADMIN y USER, y fija el stock de "Entrada Conferencia" en 1 unidad.
  • Fase 4 (Concurrencia Real con Promise.all): Dispara 2 compras simultáneas por la única entrada disponible, verificando que exactamente 1 responda 200 OK y la otra sea rechazada (409 / 400), dejando el stock final en 0 sin sobreventas.
  • Fase 5 y 6 (Seguridad RBAC): Verifica el rechazo 400 con stock agotado, el bloqueo 403 ante intento de alteración de stock o lectura de perfil ajeno, y el rechazo 401 sin token.

Comandos para Reproducir la Demostración

docker compose up -d --build
npm test

Conclusión General

El proyecto integra límites claros de microservicios, concurrencia encapsulada en el dueño del dato, seguridad distribuida con JWT y un entorno 100% reproducible con Docker.
